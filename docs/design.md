# Minecraft Cooks プラグイン 設計書

作成日: 2026-11-20
元の企画書: `claude参照可能ファイル/cooking-game-plugin-plan.md`

「(実装者判断)」は、依頼者と決めたものではなく実装者(Claude)が決めたもの。依頼者が見て違えば直す。数値はすべて設定GUIで変えられる。

## 1. 目的

マイクラサーバーのイベントとして、Overcooked のような協力料理ゲームを遊ぶ。5人1組で4〜8チーム(20〜40人)が、それぞれのキッチンで同じ注文に挑み、得点を競う。開催日は未定で、急ぎではない。大会当日に運営が困らないことを優先する。

## 2. ゴール / ノンゴール / アンチゴール

**ゴール**
- 4〜8チームが同時に、同じレイアウトのキッチンで、同じ注文の順番で遊べる
- 運営がコマンドで、チーム分けから試合の開始・終了まで進められる
- レシピは YAML、数値は設定GUIで、コードを書き換えずに変えられる

**ノンゴール**
- 試合をまたぐ通算ランキング
- キッチンの自動生成
- 皿洗い
- サーバー再起動をまたいだ試合の継続(再起動したら、その試合は無効になる)(実装者判断)

**アンチゴール**
- 運の差で勝敗が決まる
- 運営の手作業が多すぎて、大会の進行が止まる

## 3. 技術的な前提

- Paper 1.21.11、Java 21、Gradle。依存は `paper-api` だけで、ほかのプラグインには依存しない(実装者判断)
- パッケージ名は `jp.minecraftcooks`、コマンドは `/cg`、権限は `minecraft-cooks.admin`(実装者判断)
- 独自アイテムは `PAPER` をベースにし、`item_model` コンポーネントで `minecraft-cooks:<識別子>` のモデルを指定する。アイテムの種類は、PersistentDataContainer の `minecraft-cooks:id` で判別する(見た目の名前では判別しない)
- リソースパックは、運営が zip を Web 上に置き、URL を設定に書く。プラグインは、参加したプレイヤーに `addResourcePack` で送る。サーバーにもともとパックがあっても、その上に重ねて送るので、混ぜ合わせる必要はない。SHA-1 は、設定が空なら、起動時に URL から非同期でダウンロードして計算する(実装者判断)
- テクスチャ一覧は `docs/textures.md` にまとめる
- 遊ぶのは**イベント専用サーバー**(依頼者が確定)。オンラインの人は全員、参加者か運営になる。持ち物をファイルに保存して返す処理は作らない
- 参加するのは **Java版 1.21.11 だけ**(依頼者が確定)。統合版(Geyser)や、違うバージョンのクライアント向けの代わりの手段は作らない

## 3.5 持てる物(依頼者が確定)

- プレイヤーが持てるのは**1つだけ**(Overcooked と同じ)。持つ場所はホットバーの1枠目に決め、インベントリを開く、持ち替える、オフハンドに移す、といった操作はすべて止める
- 手がふさがっているときは、食材箱からもらえない。設備から取り出すこともできない
- 仲間に渡すときは、Q で床に落とす。床に落ちた物は、手が空いている人だけが拾える
- 床に落ちた物は、ラウンドの終わりにすべて消す
- 試合中は、ダメージ、空腹、PvP をなしにする(実装者判断)

## 4. キッチンと設備

### 4.1 設備のしくみ(実装者判断)

設備1つは、ブロック1マスの位置に、次の3つを重ねて作る。

| 部品 | 役割 |
| --- | --- |
| バリアブロック | 当たり判定(上に乗れない、通り抜けられない) |
| ItemDisplay | 見た目。設備のモデルを表示する。中身の食材も小さく上に表示する |
| Interaction エンティティ | クリックを受け取る。右クリックも左クリックも確実に取れる |

ブロックそのものへの左クリックは、アドベンチャーモードだと取れないことがある。そのため、クリックの検知は Interaction エンティティで行う。進み具合(調理の残り時間、切る回数)は、設備の上に TextDisplay で `■■■□□` のように出す。

プレイヤーは、試合中はアドベンチャーモードにする。

### 4.2 キッチンの登録

1つのキッチンは、キッチンID(例: `kitchen-1`)、表示名、範囲(対角の2点)、チームのスポーン地点、設備の一覧で成り立つ。設備ごとに「種類」と、必要なら「番号」(納品場所 1〜3)を記録する。

**ワンドの操作(実装者判断)**
1. `/cg kitchen create <id> <表示名>` でキッチンを作る
2. `/cg wand <id> <設備の種類> [番号]` でワンドをもらう。ワンドに「どのキッチンの、どの種類か」が記録される
3. ワンドでブロックを右クリックすると登録、左クリックすると登録を解除する
4. 範囲は `/cg wand <id> area` のワンドで、左クリックと右クリックで2点を指定する。スポーン地点は `/cg kitchen setspawn <id>` で、立っている場所にする

**複製した残りのキッチンの登録**: `/cg kitchen clone <元のid> <先のid>` で、範囲の角のずれぶんだけ、設備の位置をずらしてコピーする。先のキッチンにも、範囲だけは先に登録しておく。

登録データは `kitchens.yml` に保存する。登録した設備のエンティティ(見た目とクリック判定)は、登録したときと起動したときに出し、プラグインのタグをつけて管理する。消すときもそのタグで探す。

### 4.3 設備の種類

| 種類 | 識別子 | 動き |
| --- | --- | --- |
| 食材箱 | `box_meat` / `box_fish` / `box_veg` / `box_noodle` / `box_rice` | 右クリックで、その食材(調理前)を1つもらえる |
| まな板 | `cutting_board` | 食材を1つ置く。素手で右クリックを繰り返して切る(初期値5回)。切り終わったら、素手で右クリックして取る |
| フライパン | `pan` | 自動で調理する(4.4) |
| 鍋 | `pot_boil` / `pot_steam` / `pot_stew` / `pot_set` | 自動で調理する。動きは共通で、見た目と、使えるレシピだけが違う |
| フライヤー | `fryer` | 自動で調理する |
| 皿(盛り付け台) | `plate` | 4.5 を参照 |
| 納品場所 | `counter` + 番号1〜3 | 5章を参照 |
| ゴミ箱 | `trash` | 手に持っているものを1つ捨てる |

まな板に食材を置くときは手に持って右クリック、素手で右クリックすると切る。置いた食材を切らずに取り戻したいときは、スニークしながら右クリックする(実装者判断)。

### 4.4 自動で調理する設備(フライパン・鍋・フライヤー)(実装者判断)

- 食材を持って右クリックすると、1つ入る。最大4つまで入る
- 中身が1つ以上あると、タイマーが動く。食材を追加すると、タイマーは最初に戻る
- 完成時間になったとき、中身がこの設備で使えるレシピと**ちょうど**一致していれば、完成品に変わる。一致しなければ「失敗した料理」に変わる
- 完成してから焦げるまでの時間が過ぎると、「焦げ」に変わる
- 素手で右クリックすると、中身を取り出す。完成品・失敗した料理・焦げなら、それを1つ受け取る。調理中なら、最後に入れた食材を1つ返す(タイマーは最初に戻る)
- 失敗した料理と焦げは、ゴミ箱に捨てるしかない

例えば、シュウマイの具(切った野菜+切った肉)を茹で鍋に入れると、茹で鍋にはそのレシピがないので、失敗した料理になる。

### 4.5 皿(盛り付け台)

- 部品を持って右クリックすると、1つ載る。載っている部品が、いまの料理店のどれかの料理の部品と、種類も個数もちょうど一致したら、盛り付け済みの料理がプレイヤーの手に入り、皿は空になる(最後の部品を載せた時点で手は空いている)
- 素手で左クリックすると、最後に載せた部品が1つ手に戻る。繰り返せば、皿は空になる。持てるのが1つだけなので、全部をまとめて返すことはできない。そのぶん、うっかり左クリックしても1つ戻るだけで済む(実装者判断)
- 素手で右クリックすると、載っている部品の一覧がチャットに出る
- 皿にはどんな部品でも載せられる。間違いに気づくのはプレイヤーの役目にする(実装者判断)

### 4.6 試合の開始・終了時

- 開始時と終了時に、全設備の中身とタイマーを空にする
- 開始時と終了時に、プレイヤーのインベントリを空にする。イベント専用サーバーなので、試合前の持ち物は保存しない
- 自分のチームのキッチン以外の設備は、触っても反応しない

## 5. 注文・納品・得点

### 5.1 注文の出し方

- 各キッチンには、常に3件の注文を出す。それぞれが納品場所1〜3に対応する
- 注文は、ラウンドごとの乱数の種から作る。「k番目の注文」は全チームで同じになる。最初の3件は k=0,1,2。チームが1件送るたびに、そのチームの次の k の注文が、空いた枠に出る
- 注文の難しさ(料理の個数)は k で決まる。そのため、納品数が同じチームは、同じ注文を見ることになる

| 段階 | 対象の k(初期値) | 料理の個数 |
| --- | --- | --- |
| 1 | 0〜5 | 1〜2個 |
| 2 | 6〜13 | 1〜3個 |
| 3 | 14以上 | 2〜4個 |

料理は、いまの料理店の料理から均等にランダムに選ぶ。同じ料理が重なってもよい。

### 5.2 表示(A案)

- 各納品場所の上に TextDisplay を浮かべ、注文の中身と、入れた数を出す

```
注文 #4
ラーメン   1/2
チャーハン 0/1
```

- サイドバー: 料理店とラウンド、全チームの順位と得点
- ボスバー: 残り時間

### 5.3 納品と送る

- 料理を持って納品場所を右クリックすると、1つ入る。順番は問わない。注文にない料理も入れられる
- 左クリックすると、「もう一度左クリックで送信」と表示される。3秒以内にもう一度左クリックすると送る。うっかり送ってしまうのを防ぐため(実装者判断)。送った枠には、次の注文が出る
- 間違えて入れた料理は、素手でスニークしながら右クリックすると、最後に入れたものから1つずつ取り出せる(実装者判断)
- 空のまま送ることはできない(実装者判断)

### 5.4 得点(数値は実装者判断、設定で変更可)

注文の料理の個数を n とする。

- 満点 = 料理1個あたり100点 × n × 倍率(n=1: 1.0、2: 1.1、3: 1.2、4: 1.3)
- 間違い = 足りない料理の個数 + 余計な料理・違う料理の個数
  - 足りない量で送った場合も、足りない分を間違いに数える(依頼者が確認済み)
- その注文の得点 = 満点 − 間違い × (満点 ÷ n)。0点より下にはならない
- ラウンドの終わりに、そのラウンドの合計点から、合計点 × 0.25% × そのラウンドの間違いの総数 を引く。1点未満は切り捨てる

例: ラーメン2個+チャーハン1個(n=3、満点360)に、ラーメン1個とシュウマイ1個を入れて送った場合。足りないのはラーメン1個とチャーハン1個、余計なのはシュウマイ1個で、間違いは3。得点は 360 − 3×120 = 0点 になる。

### 5.5 順位

- クイックマッチはそのラウンドの得点、ノーマルマッチは3ラウンドの合計点で決める
- 同点のときは、最後のラウンドの得点が高いチームを上にする。設定で「間違いが少ないほう」「同順位のまま」にも変えられる

## 6. レシピ

`recipes.yml` に、店・料理・工程・部品を書く。工程は「設備の種類」「入れるもの(個数つき)」「できるもの」で表す。**工程は店ごとに定義する**。例えば、鍋で「切った肉+切った野菜を煮る」と、フランスではポトフ、和食では肉じゃがになるので、いま遊んでいる店の工程だけを使う。

| 店 | 料理 | 工程 | 皿に載せる部品 |
| --- | --- | --- | --- |
| 中華 | ラーメン | 麺→茹で鍋→茹で麺 / 肉→茹で鍋→茹で肉→まな板→切った茹で肉 / 野菜→まな板→切った野菜 | 茹で麺+切った茹で肉+切った野菜 |
| 中華 | シュウマイ | 切った野菜+切った肉→蒸し鍋→蒸したシュウマイ | 蒸したシュウマイ |
| 中華 | チャーハン | 切った野菜+切った肉+米→フライパン→炒めたチャーハン | 炒めたチャーハン |
| フランス | テリーヌ | 切った肉(または切った魚)+切った野菜→固め鍋→固めたテリーヌ | 固めたテリーヌ |
| フランス | ムニエル | 魚→フライパン→焼いた魚→フライパン→よく焼いた魚 | よく焼いた魚 |
| フランス | ポトフ | 切った野菜+切った肉→煮込み鍋→煮込んだポトフ | 煮込んだポトフ |
| 和食 | 天ぷら | 魚→まな板→切った魚→まな板→細かく切った魚→フライヤー→揚げた天ぷら | 揚げた天ぷら |
| 和食 | 肉じゃが | 切った肉+切った野菜→煮込み鍋→煮込んだ肉じゃが | 煮込んだ肉じゃが |
| 和食 | おそば | 麺→茹で鍋→茹で麺 / 肉→フライパン→焼いた肉 | 茹で麺+焼いた肉 |

テリーヌの「固める」は、鍋の一種(見た目だけが違う固め鍋)として扱う(実装者判断)。

### 調理時間の初期値(実装者判断)

| 工程 | 完成まで | 完成から焦げるまで |
| --- | --- | --- |
| 切る | 5回クリック | (焦げない) |
| 焼く・炒める(フライパン) | 8秒 | 8秒 |
| 茹でる | 10秒 | 10秒 |
| 蒸す | 10秒 | 10秒 |
| 煮る | 12秒 | 12秒 |
| 固める | 12秒 | 12秒 |
| 揚げる | 8秒 | 8秒 |

## 7. 試合とチーム

### 7.1 チーム分け

- 参加者は、試合開始の時点でオンラインのプレイヤーのうち、運営が「不参加(運営・観戦)」に指定していない人
- 自動: ランダムに5人ずつ分ける。5で割り切れないときは、**余った人をランダムに選んで観戦に回す**(依頼者が確定)。参加者が40人を超えたときも、超えたぶんは観戦に回す(実装者判断)
- 手動: `/cg team add <チーム> <プレイヤー>` などで指名する。手動のときは5人ちょうどでなくても開始できる(テスト用。警告は出す)(実装者判断)
- 分け終わったら、チャットに編成と観戦者の一覧を出す。運営が確認してから `/cg match start` で始める
- チームの名前と色は、`/cg team name` と `/cg team color` で変えられる。初期は赤・青・緑・黄・紫・水色・橙・桃
- 試合中は編成を固定する。途中で抜けた人が戻ってきたら、同じチームとキッチンに戻す。抜けた人の代わりは入れない(実装者判断)

### 7.2 試合の流れ

1. `/cg match start quick [店]` または `/cg match start normal`。キッチンがチーム数より少なければ、開始できない
2. チームとキッチンを1対1で割り当てて(ランダム、または事前に `/cg team kitchen <チーム> <キッチン>` で指定)、テレポートする
3. 全チーム一斉に、カウントダウン(5秒)
4. ラウンド(初期値5分)
5. ラウンドの結果を表示して、休憩(初期値30秒)。ノーマルマッチは次のラウンドへ
6. 最終結果を表示して、全員を元の場所に戻す

### 7.3 運営のコマンド

| コマンド | 内容 |
| --- | --- |
| `/cg match start quick [店]` / `start normal` | 開始。店を省略したら、ランダムに決める |
| `/cg match pause` / `resume` | 一時停止・再開。止めている間は、調理タイマーも止まる |
| `/cg match stop` | 強制終了 |
| `/cg match redo-round` | いまのラウンドをやり直す(そのラウンドの得点を捨てて最初から) |
| `/cg team auto` / `add` / `remove` / `move` / `name` / `color` / `list` / `clear` | チームの管理 |
| `/cg exclude add|remove <プレイヤー>` | 不参加(運営・観戦)の指定 |
| `/cg score add <チーム> <点>` | 得点の手動調整(マイナスも可) |
| `/cg kitchen create|remove|list|setspawn|clone|reset` | キッチンの管理。`reset` は設備の中身を空にする |
| `/cg wand ...` | 4.2 を参照 |
| `/cg spectate [キッチン]` | 観戦。スペクテイターモードで、そのキッチンに移動する |
| `/cg settings` | 設定GUIを開く |
| `/cg reload` | レシピとメッセージを読み込み直す(試合中はできない) |

観戦者と、試合が終わったチームのプレイヤーも、`/cg spectate` を使える。

## 8. 設定GUI

チェストのメニューで、次の値を変えられる。変えたら、すぐ `settings.yml` に保存する。クリックで±し、シフトクリックで大きく変わる。

- ラウンドの制限時間、休憩時間、カウントダウン
- 注文の件数(初期値3。納品場所の数が上限)
- 難しさの切り替わり(段階ごとの k と、料理の個数の範囲)
- 調理の種類ごとの、完成までの時間と焦げるまでの時間、切る回数
- 料理1個あたりの点数、個数ごとの倍率、減点の割合(0.25%)
- 同点のときの決め方

レシピ(`recipes.yml`)とメッセージ(`messages.yml`)は、ファイルで編集する。

## 9. 検討した方式

**キッチンの用意**: 運営が建てて登録する方式(案A)を、依頼者が選んだ。設計図からの自動生成(案B)は、実装が重いので見送った。

**注文の表示**: 納品場所の上に浮かぶ文字+サイドバー+ボスバー(A案)を、依頼者が選んだ。サイドバーだけ(B案)は、15行に収まらないので見送った。注文票アイテム(C案)は、開く手間がゲームの速さに合わないので見送った。

**設備の見た目**: 見えないブロック+専用モデルの表示(依頼者が賛成)。クリックの検知に Interaction エンティティを足したのは、実装者判断。

**リソースパック**: URL を設定に書く方式(実装者判断)。プラグインの中に Web サーバーを持つ方式も考えたが、サーバーのポートを開ける必要があり、運営の手間が増えるので見送った。

## 10. 作る順番(実装者判断)

1. 土台: Gradle、設定の読み込み、独自アイテム、レシピの読み込み
2. 1キッチンで、食材箱 → まな板 → 鍋 → 皿 → 納品 が動く
3. 全設備、全9料理、注文と得点
4. チームと試合の進行(クイック → ノーマル)、表示
